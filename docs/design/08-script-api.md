# Campfire — Script API

Derived from the reference packages in `source/packages/moba/`, six heroes, the player spells and the 3v3 mode, and from what the genre proofs need ([Genres](04-capabilities/genres.md#genre-proofs)). Every name is used there; a name neither needs is not here. The [reference](08-script-api-reference.md), which the registry writes, lists every name with its roles, capability and whether the release runs it.

Each call, handle field and hook belongs to the core or to one capability ([Capabilities](04-capabilities/00-overview.md)); a package gets those of the capabilities it declares, and the load checks refuse the rest. The reference names each one's capability.

## Rules

- **Data first.** What the engine can do from data, it does: effects of actions, deliveries and intervals, held modifiers, charges, charged actions, projectiles, areas, auras, shields. Scripts describe only what is special about an effect.
- **Hooks by name.** The engine calls a script function by its hook name: `on_<event>` for what happened, `calc_<value>` for a pure hook that returns a value. Hook names differ between roles (action, modifier, mode, AI), so one file can serve an action and the modifiers it applies. An event's data list and its hook share the name, and the list runs first.
- **Handles read, `ctx` changes.** Handles are read-only, except `.state` and a modifier's `.stacks`, which a call may write and read back. Every other change goes through `ctx` and is queued: the call is all-or-nothing ([Scripting](02-engine-core.md#scripting)).
- **Default source.** `ctx` knows the acting unit: the unit whose action runs, the source of a projectile or an area, or a modifier's source. Damage, heals, modifiers, projectiles and areas come from it unless a call names another.
- **New units at once.** `spawn_unit`, `ctx.projectile` and `ctx.area` return a `NewUnit`, which holds the id the call took for the unit: the call can give it to `grant`, and write and read back its `.state`, but reads none of its other fields. A unit the mode spawns appears when the call commits, and a delivery later in the tick, each with the id the call took and what it wrote.
- **Event order.** A call's effects apply in call order. The hooks they trigger are queued first-in first-out and run after all of the call's effects. A hook of a modifier that is gone by then is skipped. A chain longer than an engine constant fails with `script_error`.
- **Dead and despawned units.** A handle keeps returning the unit's last values, and `alive` is false. Effects on a dead unit do nothing, except `respawn`. A modifier whose source despawned keeps that source's last stats.
- **Values are live.** `ctx.p` resolves when it is read, with the current rank and the current stats of the source.
- **Pure hooks.** `calc_damage` and `calc_heal` return a value; their `ctx` refuses effects.
- **Handles last one call.** A call sees the units as its stage began; a handle is valid within the call. `unit.target` is `()` when the unit has no target, or its target is gone. `unit.recent_attackers(ms)` lists the living units that struck it within the last `ms`, rounded up to whole ticks.
- **Queries.** Lists are sorted by stable id; `nearest_visible` sorts by distance, then id. `find`, `find_visible` and `nearest_visible` return only living targets ([Combat](04-capabilities/combat.md#death-and-respawn)): never dead units, units with no life pool, such as projectiles and areas, or units whose tags block `target`; `avatars` and `units_tagged` return the dead too, so a mode sees a structure that fell. `find` includes units hidden from the caller's group, for effects on an area; `find_visible` and `nearest_visible` return only what that group sees, for choosing a target, and `unit.can_see(other)` tells whether the unit's group sees `other`. What a group sees is what the Vision stage of the last tick found; without `vision`, every group sees every unit. Distances are in the map's metric, and a radius reaches a body to its edge ([Reach](04-capabilities/00-overview.md#space-and-map)): `find` from a point, `nearest_visible` from the edge of `of`'s body, as a weapon's range, its order by the distance between centres. `pos.within(other, r)` measures between two points, which have no bodies.
- **Numbers.** [Game Scripting](03-game-scripting.md#numbers). `num(i)` makes a `Num` from an integer. `Num` has `min`, `max`, `clamp`, `round`, `floor`, `ceil`; `round` and the others return integers. The operators, the comparisons, `min` and `max` take an integer on either side.
- **Randomness** comes only from `ctx.chance` and `ctx.pick`, both from the secret streams: `script.draw`, one sequence for each acting unit and tick, and `script.mode`, one for the mode's own calls each tick: each draw takes the next words of that sequence, so draws follow the order the calls run in, which is the same on every machine, and the server alone runs them. `ctx.chance(p)` is true with probability `p`, exactly, and fails for a `p` below 0 or above 1; `ctx.pick(list)` is an entry of `list`, each as likely, exactly, and fails for an empty list. An attack's roll is drawn by `combat`.
- **Vectors.** `a + b` and `a - b` add and subtract two vectors, and `v * n` and `n * v` scale one by a number, each rounded once to the nearest; a result past what a number holds fails the call. A vector is no place: a call that takes a place keeps it within the bounds, as every move does.
- **Time** is in milliseconds, rounded up to whole ticks.
- **Rhai names.** Rhai's reserved words cannot be names, including `spawn` and `match`.

## One source

The registry replaced the hand-kept lists the load check read (a table of `ctx` names beside three `ctx` types that each registered their own), which drifted from what the engine runs: a name loaded that no code ran, or that one role ran and another did not.

Established engines keep one source for what scripts may use, and derive everything else from it. Godot's `ClassDB` is filled by the same `bind_method` call that binds the code; the script analyzer and the editor read it, and the build fails when the class reference does not list exactly what it holds. Roblox's API dump is generated from the engine's reflection, each member tagged with the contexts that may use it and the security they need, and the engine enforces those tags when a script calls. Factorio publishes its runtime API as a machine-readable file per stage, which its documentation and tools read. The campfire registry follows them:

- **Registration is declaration.** Every name a script may use, a `ctx` call or value, a handle's field or method, is registered by one builder call that both binds the function to Rhai and records the entry: its owner (`ctx`, unit, modifier, damage, heal, position, number), its name, whether it is a value, a call, a field or a method, the roles that may use it, its capability, its signature and a one-line description. No name exists in one place and not the other.
- **One `ctx`.** One `ctx` type serves every role. Its frame holds the role, the acting unit, the params it reads, the mode's state as a mode call sees it, the players' resources and the effects it queues; a call is registered once, for every role design 08 gives it, so a call written for abilities runs in a mode script without a second copy. A call given to some roles only checks the frame's role when it runs, as Roblox checks a member's context, so it fails as the API's refusal even if a check above missed it.
- **Effect queues.** Each capability's calls queue its own effect types, one queue a type, and each type applies itself; the effects apply in call order, whatever their types.
- **Hooks, tag effects and data fields** are registered by the code that runs them: the system that calls a hook, with its parameters' names, the system that asks a tag effect, the code that reads a data field. A test holds the registry's data fields equal to the names serde reads for each table, and another holds the registry equal to the functions the engine binds, by name and first parameter.
- **Planned names.** A name design 08 gives that no code runs yet is registered as planned, for its roles, with no function. The reference lists it as planned, so what the release does not run is visible in one place. The load check refuses a planned name, as it refuses a name the registry does not hold: a script that uses one, a data field and a hook alike fail the load, with the name and where it stands.
- **The checks read the registry.** A `ctx` name loads only for a role it is registered for, of a capability the mode declares. A field or method a script reads on any other value must be one some handle has, one the engine has of its own (Rhai's packages and `Num`'s, which the registry reads from the engine), a key of the script's object-map literals, or one of the script's own functions; the names after `p`, `state` and `params` name data, which the data checks read. A dynamic script gives no type to check against, so the check is by name, and a field read on the wrong handle still fails at run time.
- **The reference is generated.** The tables of `ctx`, handles, hooks, tag effects and data fields come from the registry, into the [reference](08-script-api-reference.md), with each name's roles, capability, status, the package API version it came in, and description; a test fails when the checked-in reference differs from what the registry writes, as Godot's build does for its class reference. The rules stay prose here.

The registry reads Rhai's own list of functions (`Engine::collect_fn_metadata`, from its `internals` feature) for the engine's built-ins, and a test reads it to hold the registry equal to what the engine binds; Rhai holds no roles, capabilities or status, so the registry is campfire's, and Rhai stays its binding.

## Filters

One set of words selects units everywhere: `targeting`, projectile `hits`, area `affects`, aura `affects`, player modifiers, weapons, and every query. A filter is a relation, then tags, each after a colon and each with an optional `!` that negates it: `enemies`, `allies:avatar`, `enemies:avatar:!stunned`, `enemies:air`. The relations are those of the teams ([Relations](04-capabilities/00-overview.md#relations)): `enemies` hostile and neutral, the units that may be attacked; `hostiles` hostile; `neutrals` neutral; `allies` friendly, the unit itself included; `all` every one. The tags are a unit's whole set ([Tags](04-capabilities/stats.md#tags)): its type's, those the engine gives it, and those its modifiers grant. A relation selects units with the `projectile`, `area` or `item` tag only when the filter names that tag. `targeting` and projectile `hits` also take `none`, which selects no unit.

## Data files

Arrays in the fields and params of an action are per rank: one entry for each rank of its slot kind. Anywhere else an array is a list.

**Param values** (`[params]`, read as `ctx.p.<name>`; an unknown name is an error):

| Form | Example | Value |
| --- | --- | --- |
| Integer | `slow_ms = 2000` | the integer |
| Decimal string | `radius = "3.0"` | a `Num` |
| Array | `slow = ["0.15", "0.20", "0.25", "0.30", "0.35"]` | the entry for the current rank |
| Scaling table | `{ base = [80, 120, 160, 200, 240], ability_power = "0.65" }` | `base + per_level × (level − 1) + Σ ratio × stat` of the source, as a stat's value at a level is |

A scaling table's keys are `base`, `per_level`, and a ratio for any stat the mode declares, by its name; under `bonus`, a ratio of the part of a stat above its type's value: `{ base = 60, bonus = { attack_damage = "0.5" } }`. Its `base` holds numbers, so an integer past what a number holds fails the read of the data. Its sum rounds once, and a sum that leaves the range of a number stops at its end, as a stat's sum does ([Stats](04-capabilities/stats.md#stats)), so a scaling param always has a value. A number field anywhere in data may be `{ param = "<name>" }`, resolved in the same way. An action's `range`, `cooldown_ms`, `cost` and `windup_ms` resolve when the action loads, one value for each rank, so a param they name is a value or a per-rank array, not a scaling table.

**Manifest** (`manifest.toml`): `name`, `version`, `api` (the package API version it targets, `"major.minor"`; [Package API](03-game-scripting.md#game-package)), `language` (the language of its own text) and `kind`: `locale` (Fluent files that add a language to the packages it depends on), `mode`, `avatar` (a unit type players choose, such as a hero), `loadout` (actions players choose, such as spells) or `campaign` (missions, each a mode it depends on, with `opens_when`, a `bool` field of its carry that opens the mission, and the `[carry]` schema its missions share). A mode's also has `capabilities` (none twice, not `mode`, and each with the ones it builds on: `combat` on `stats`, whose pools hold its life, and `progression` on `stats`; `abilities`, `projectiles`, `areas` and `vision` on `combat`; `orders` on `combat` and `navigation`; `items` on `stats`), `tick_hz = { min, max, default }` (all positive, `min ≤ default ≤ max`), `teams` (each `{ name, slots }`, any number; their slots in order make the player slots; a team with no slots, such as a MOBA's camps, has only units), `backends`, `max_move_speed` (m/s, positive), `script_limits = { per_call, player, think, mode, systems, generate }` (each pool holds a whole call; each player slot has a pool of the size `player`), `[dependencies]`, each named by its package's name, and in the workspace given by path, and `load_order` (the dependencies in the order they load, the last winning an override; by name when absent), and `[overrides]` (the records of dependencies it replaces, by package and id). An avatar's id is its package's name.

**Mode** (`data/mode.toml`): `script`; a capability's settings in its own section, as a unit type's are: `[combat]` with `damage_kinds` (at least one), `assist_window_ms` and the bindings ([Combat](04-capabilities/combat.md#data)), `[navigation]` with `layers` ([Navigation](04-capabilities/navigation.md#data)), `[clock]` with `time_scale` and `start` ([Game clock](04-capabilities/00-overview.md#game-clock)), `[saves]` with `by` (`player`, the default, or `mode`) and `autosave_ms`; and the records: `[stats]`, `[pools]` and `[tags]` ([Stats](04-capabilities/stats.md#data)), `[[slots]]` ([Actions](04-capabilities/actions.md#data)), `[[relations]]` ([Relations](04-capabilities/00-overview.md#relations)), `[choices]` ([Choices](04-capabilities/control.md#choices)), `[tracks]` ([Progression](04-capabilities/progression.md#data)), `resources` (the players' resources), `[carry]` (typed, with a `carry_version`, as `[state]`), `[inputs]` (name and type of each player input: `string`, `string_list`), `[state]`, `[params]` (values, or lists whose entries are values or strings, such as unit types), `[modifiers]`, `[actions]`, `[items]` and `[shop]` ([Items](04-capabilities/items.md#data)), `[perks]`, `[recipes]`, `[tables]`, `[quests]`, `[topics]` and `[systems]` ([Scripted systems](04-capabilities/00-overview.md#scripted-systems)). An input that does not match its type never reaches the script.

**Units** (`data/units.toml` of a mode, or the one unit type of an avatar package): `[units.<id>]` with `tags`, `params`, `[state]`, and a section for each capability the unit type uses ([Unit types](04-capabilities/00-overview.md#unit-types)): `stats` (`stat = { base, per_level }`), `pools`, `tracks`, `slots` (its package's action ids by slot kind), `passive` (a modifier it holds from its spawn), `combat` (`on_death`), `orders`, `character`, `vision`, `collision` (`radius`, `layer`), `hitboxes`, `item`, `inventory`, `use`, `enter`, `node`, `drop_off`, `projectile`, `area`. An avatar package's unit type has `name` too, and its package's `[actions.<id>]` and `[modifiers.<id>]`; its field is `slots`, not `actions`, so the one file holds both. An avatar or a loadout package holds the types its actions deliver in `[units.<id>]`: tags, params, a `projectile` or `area` section and a `vision` section, nothing more. Its actions name them by `<id>`, in its own scope: a unit type's identity is its scope and its name, so no two packages' types share one. The mode's scope holds the mode's unit types, and each avatar by its package's name; what the mode's data and scripts name is in it, and its own actions name their delivery types in it too. A package's own scope holds its delivery types, which only its actions name; `unit.unit_type` gives a type's name in its scope. A mode's own delivery types are in its `data/units.toml`, with the same sections alone, and no map or train places one.

**Actions** (`[actions.<id>]`): [Actions](04-capabilities/actions.md#data). **Modifiers** (`[modifiers.<id>]`): [Stats](04-capabilities/stats.md#data).

**Map** (`map/map.toml`): `metric` (`planar` or `spatial`), `[bounds]` (`min` and `max`, each `[x, z]`, `min` below `max` on both axes: no unit is ever outside them), `[grid]` (`cell` in meters, positive: whole cells over the bounds, at most 2²² cells, and `[[grid.brush]]`, each a simple polygon of `points` ([Vision](04-capabilities/vision.md#grid-fog-of-war)); a mode with grid vision needs it), `[navigation]` (`cell`, the same rules, and `[[navigation.walls]]`, each a `layer` and a simple polygon of `points` ([Navigation](04-capabilities/navigation.md#data)); a mode with `navigation` needs it), `[[paths]]` (`name`, `points`), `[[units]]` (`unit_type`, `team`, `pos`, and `path` with `from` if it walks or guards one: they stand from the start), `[[markers]]` (`name`, `tags`, `pos` or a `region` with `min` and `max`, a box, `team`, `params` and `events`, each optional but `name` and `tags`). A map with an `on_generate` script may leave out what the script builds. A point is `[x, z]` in meters on the ground plane, or `[x, y, z]` with `spatial`.

**State types:** `int`, `num`, `bool`, `string`, `entity`, `entity_list`, `pos`, `vec`; each with a `default` and, for the mode's and a unit type's state, `sync`, which is `none` when the field does not give it ([Unit state](03-game-scripting.md#script-state)). A modifier's state takes no `sync`.

**The reference MOBA's stats, pools and tags** (in `data/mode.toml`; the engine reads some by name or binding ([Stats](04-capabilities/stats.md#stats))):

| Stats | Limits |
| --- | --- |
| `health`, `health_regen`, `mana`, `mana_regen`, `energy`, `energy_regen`, `attack_damage`, `ability_power`, `armor`, `magic_resist`, `armor_pen`, `magic_pen`, `move_speed`, `physical_block` | — |
| `healing_received_pct`, `damage_dealt_pct` | ≥ −1 |
| `attack_speed` | ≤ 2.5 attacks per second |
| `crit_chance`, `armor_pen_pct`, `magic_pen_pct`, `life_steal`, `spell_vamp` | 0 to 1 |

Pools: `health`, `mana` and `energy`, each with its stat and its regen. `[combat]`: `life = "health"`, `leech = { attack = "life_steal", other = "spell_vamp" }`, `heal_scale = "healing_received_pct"`; its `calc_damage` crits when `d.roll` is below the source's `crit_chance`. A slow is a `cut` of `move_speed`, and every slow modifier grants the tag `slowed`. Slots: `basic` (5 ranks), `ultimate` (3 ranks), `spell` (the loadout) and `weapon`; the levels each rank needs, 1, 3, 5, 7 and 9 for `basic` and 6, 11 and 16 for `ultimate` ([Reference MOBA](07-reference-moba.md#rules)), come into the data with learning ([Progression](04-capabilities/progression.md)).

## Engine enums

A value of a fixed set the engine owns reaches a script as a member of an enum, not as a string: `Relation::Hostile`, `Relation::Neutral` and `Relation::Friendly` for `set_relation`, and `PathEnd::Start` and `PathEnd::End` for `spawn_group`. These are the engine's two such sets today; a call that takes a value of a fixed set takes it this way.

Established engines draw the same line. Factorio gives scripts the engine's fixed sets as `defines`, `defines.events.on_tick`, and names the prototypes mods declare by string, `"iron-plate"`; Roblox gives `Enum.Material.Plastic` for its sets and names instances by string; Godot binds each class's enums as constants. The engine's sets are known when the engine is built, so they can be values the language checks. A mode's names, its stats, tags, damage kinds and the rest, are known only when its packages load, so they stay strings, which the load checks ([Checks at package load](#checks-at-package-load)).

- **Registration.** One builder call declares an enum: it binds a static module of constants, one for each member, under the enum's name, and records the enum in the registry with its members. The reference lists every enum and its members.
- **Values.** A member is a value of its enum's type. A script compares two with `==` and `!=`, passes one to a call, and keeps one in a variable or in script state; `to_string` gives the name data uses, `"hostile"`. Rhai's `switch` takes only literal cases, so a script tests a member with `if`.
- **Calls take the type.** A call's parameter is the enum's Rust type, so the call resolves no name as it runs. A string given in its place fails the call, as a call of another signature fails.
- **Data.** A data file names a member by its name, `relation = "hostile"`, which serde reads into the same type. A value that reaches a script as data text, such as a marker's param, becomes a member through the enum's `named` function, `PathEnd::named(text)`, which fails the call for a text that names no member.
- **Load checks.** The registry marks each argument that takes an enum, as it marks a name. The load refuses a string literal given to such an argument, and a `Module::name` path whose name is neither a member of the enum nor its `named`. The load compiles each script with the engine a match binds, so Rhai's strict variables mode refuses a module that is no enum's, as the engine has no other module; it finds an unknown member only when the call runs, so the load checks the members.
- **Strict variables.** Scripts compile in Rhai's strict variables mode: a variable that no `let`, `const`, parameter or loop defines before its use fails the compile, so `castr` for `caster` is a load error, not a script error in a match.

**Not constants: a mode's names.** Its names stay strings for three reasons. A declared name can be a Rhai keyword: the reference mode's damage kind `true` cannot be `DamageKind::true`. An avatar or a loadout plays in every mode that depends on it, so a stat or a tag it names is the mode's, known only for a given mode. And a modifier is the package's own while a stat is the mode's, so the constants would come from two places a script cannot tell apart.

## Handles

A unit handle has the fields of the sections its type has; reading a field it lacks is a script error. Projectiles, areas and items are units, with the fields of their sections. The [reference](08-script-api-reference.md) lists each handle's fields and methods.

## `ctx`

The [reference](08-script-api-reference.md) lists every value and call of `ctx`, with the roles it serves.

**Walking.** A unit a move order, a chase or a path sends somewhere walks a route there on its layer's `[navigation]` cells: round structures, then round units that stand in its way or keep it back ([Navigation](04-capabilities/navigation.md#movement)). A goal it cannot stand on ends its route at the nearest place it can.

`ctx.p` reads, in an action, its params; in a modifier, the modifier's params and then those of the action that applied it; in a mode or AI script, the mode's params.

**Mode calls.** The map's placed units spawn, then `on_match_start` runs, before the first tick. A timer counts from its call, in ticks rounded up, at least one, and fires in the Mode stage at the end of a tick: set before the first tick, 1 ms fires at the end of tick 0. `ctx.teams` names the teams, `ctx.players` counts the session's players, and `ctx.team_of(player)` names a player's team; `enemy_team` needs a mode of two teams with slots. `ctx.map.markers(tag)` lists the markers of a tag, each with its `name`, `pos`, `team` and `params`. `spawn_unit(type, team, pos)` and `(type, team, pos, player)` fail for a point outside the map's bounds, and for a type that is not the mode's own or an avatar: a projectile or an area type comes only from its action; the unit spawns when the call ends, and the call gets the new unit, for `grant` and its `.state` ([Rules](#rules)). `spawn_group(team, path, from, types)` spawns its units in order at the path's `from` end, `PathEnd::Start` or `PathEnd::End`, walking it from there. `choose`, `chosen` and `available` read and record players' choices ([Choices](04-capabilities/control.md#choices)); `grant` puts actions in a unit's slot kind, after its slots of that kind. `on_unit_died` runs after the due timers, once for each unit that died in the tick, in the order they died; `killer` is `()` when no damage of a source killed it. A death whose call finds the mode pool spent waits, with those after it, for a later tick, and runs there before that tick's deaths; its unit stays, dead, until then, a killer gone by then is `()`, and an assister gone by then is left out. `respawn` takes a dead unit whose type stays dead, and refuses a living one or one whose type despawns ([Combat](04-capabilities/combat.md#death-and-respawn)). `set_relation(a, b, relation)` changes how two teams regard each other, `relation` a member of `Relation` ([Engine enums](#engine-enums)). `save()` asks for a save at the end of the tick; `carry` reads the carry the session loaded and is written for the next session ([Saves](02-engine-core.md#saves)); `generate(region)` builds a region of the map through `on_generate` ([Space and map](04-capabilities/00-overview.md#space-and-map)). A player's mode input is a command of the `mode` owner: its name, then its value in its declared type, in postcard.

## Hooks

The [reference](08-script-api-reference.md) lists every hook, with its parameters, role and capability.

A unit type's `passive` is a modifier it always carries. `combat` finds takedown participants once, with the mode's `assist_window_ms`: they receive `on_takedown`, and the mode receives them as `assisters`.

## Checks at package load

A package loads only when all of these pass:

- No data file holds human text: names, descriptions and lines are message ids, each of which the file of the manifest's `language` defines.
- Every data file matches its schema, every per-rank array has one entry for each rank of its slot kind, and every field of an action (`range`, `cooldown_ms`, `cost`, `windup_ms`) holds at every rank. A field an action's kind does not use fails.
- Every name data declares or names is a declared name: a lowercase letter, then lowercase letters, digits and underscores. These are the ids of actions, modifiers and unit types and every name in data that refers to one, params and the params a number reads, tags and the tags of a filter, teams, paths, markers and their tags, the mode's inputs, and the fields of every state. A package's name is not one, as it names the package to people too.
- The mode declares at most 256 tags together, the engine's three among them, and no avatar has the name of one of them. No unit type or modifier carries `avatar`, `projectile` or `area`, which only the engine gives.
- No avatar names `orders`: a player controls it, and a bot plays it through player inputs ([Control](04-capabilities/control.md#ai)).
- Every unit type that stands makes a unit at level 1, as a match builds it: each pool's maximum a stat the type gives, positive at level 1 as the stat book computes it, within the stat's limits, and the life pool with `combat`. A move speed below 0 walks no step, as the stat book keeps a speed from 0 to the cap. Every AI's script defines `on_think`. Every time of an action and every AI's think period counts in ticks at the fastest rate the manifest's `tick_hz` allows, where a time counts the most ticks, so it counts at every rate a session may choose. A match start then fails only on the session's terms.
- Every script is referenced by data. Every function named like a hook, a hook's name or any name that starts with `on_` or `calc_`, is a hook of a role the script serves, with the hook's parameters, so a misspelled hook is an error, not a hook that never runs.
- Every modifier id, action id, `ctx.p` name, `{ param }` reference, stat, pool, player resource, tag, track, team, path, unit type, slot kind, layer, filter, damage kind, choice and marker tag that a script or data file names exists. Scripts are read with `AST::walk`, from Rhai's `internals` feature. The registry marks each argument of the script API that is a name, and of which kind, and the reference lists them; the load checks each string literal a script gives such an argument. A name a script computes at run time is checked at its call.
- Every way a modifier is applied, by data or by a script's literal name, gives each param the modifier reads, at every rank it applies the modifier at ([Stats](04-capabilities/stats.md#modifiers), Appliers).
- Every string literal a script gives an argument that takes an engine enum fails, and every `Module::name` path names a registered enum and one of its members or its `named` ([Engine enums](#engine-enums)). Every script compiles in Rhai's strict variables mode.
- No script makes a function pointer: no anonymous function or closure, `|x| ...`, and no `Fn(...)`, so nothing calls `call` or `curry`. A closure that captures `ctx` uses it outside the forms the `ctx` checks below see, and no reference package needs one.
- Every `ctx` name is one the registry holds, as a value or a call as the script uses it, for a role the script serves, of a capability the mode declares. Every field or method the script reads on another value is one the registry or the engine has, a key of its object maps, or one of its functions ([One source](#one-source)).
- Every value of `ctx` is a variable named `ctx`, so the checks see all its uses: every hook's first parameter is named `ctx`; `ctx` is used only as `ctx.<name>` or as a whole argument of a call, not of an operator; a function of the script that receives it names that parameter `ctx`; and no `let`, `const` or `for` binds a new `ctx`.
- Every capability a package's data or scripts use is declared, and each builds on the ones it needs. A name the registry plans loads until the release runs it, and fails when a script uses it; the reference lists each.
- The manifest's capabilities, tick rates, pools and move speed cap hold, where the manifest is read. Every package targets a package API this release serves: the same major, a minor no higher; every homing projectile flies faster than the cap.
- Every delivery names a projectile or an area type of its action's package, as [Deliveries](04-capabilities/actions.md#deliveries) limits it; every unit type with a delivery section has tags, params and state beside it alone, every unit type of an avatar or a loadout package is one, and no avatar is.
- The map and the teams name only what the mode has: every placed unit's unit type, team and path; every marker's tags and team; every point of the map within its bounds; every spawn marker and waypoint a place the widest unit of its layer that walks may stand among the placed units, and every waypoint reachable from the one before ([Navigation](04-capabilities/navigation.md#map-checks)); no two teams, paths, markers of one name or entries of a choice alike, and no pool with the name of a player resource; every relation naming two teams of the mode.
