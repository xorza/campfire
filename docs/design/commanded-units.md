# Slice: Commanded units

At its end, the player selects a hundred units of a Zero Hour base start in the client and moves them, and every one walks, where an order to more than 24 is dropped now; the Zero Hour check plays under the terms the client plays and drops no input. The facts are in [The size of an order to a group](../research/order-size.md).

## Decisions

- **An input holds 1,024 bytes.** `InputRules::LAN` lets a payload hold 1,024 bytes, Zero Hour's retail bound on a message, which one of Campfire's 1,200-byte datagrams carries, as Zero Hour and Spring let one message fill about a packet; a player then holds at most 126,976 bytes of inputs on the server. Refused: 64 bytes, under which a move holds 24 units at most and fewer as ids rise.
- **A player's orders go to its commanded units.** Each player holds the units its orders command, which a select sets, and an order names no units of its own, as Zero Hour's `MSG_CREATE_SELECTED_GROUP`, Spring's `NETMSG_SELECT` and StarCraft II's selection deltas set the units each command goes to; an order to the units it commanded last sends no ids again. Refused: the ids in each order, whose size grows with its group and its ids, under any bound; the client's split of a group order, which plans one route for each part ([One command, one route](04-capabilities/navigation.md)).
- **A select is the players' command.** A payload's command goes to a capability or to the players, who read a select in Inputs before any capability reads its orders, so production's and items' orders need no `orders` module. Refused: a select among `orders`' directives, which every mode of production would need; a capability that is no module.
- **An order goes to the units commanded at its place.** Each order of a tick goes to the units the last select before it set, in the order of the inputs and of their commands, so a select and an order in one input, or a select between two orders of one tick, commands what its client meant; the commanded units the tick ends with are the player's state. Refused: every select of the tick first, which sends an order before a later select to the later units.
- **A select holds what its player controls.** A select keeps, in increasing stable id, each unit it names that stands and that its player controls, a leader as its order expands it ([An order to a leader is its spawns' order](04-capabilities/control.md)), so what a player commands is bounded by its units; a select past one payload continues in the next input, which adds to it. Refused: every id a client names, which grows without bound.
- **The commanded units are their player's prediction.** They are sent to their player alone, as an enemy's selection tells another player what it plans, and a predicting client applies its own selects as it applies its orders, so its prediction commands what the server will. Refused: state the client keeps apart from the match, which a rollback to the server's state leaves behind.
- **A client and a bot send a select when the units differ.** The client puts a select before an order in the same input when its selection differs from the units its predicted match commands, and a bot's driver when its order's units differ from those it sent last, so an order to the same units costs no ids. Refused: a select for every change of the client's selection, which logs a player's every click.
- **The checks play under the client's terms.** The tests' sessions and the Zero Hour check's plays take `InputRules::LAN`, the check's plays count in their golden each bot input the session log refuses, by the rule the server's bot driver drops it by (`Session::serve_bot`), and fail on an input of the check's own player that the log refuses, so a bound the client plays under shows in a check. Refused: roomier terms for tests and checks, under which the check passed while the client dropped orders and which no test needed; a check that stops at a bot's refused input, where the server drops it and plays on.

## Checks

- **A group of any size moves.** A scripted match selects 300 units and moves them: one select and one order, and every unit walks.
- **An order goes to the units commanded at its place.** In one tick, an order, a select of other units and a second order: the first goes to the units commanded before, the second to the new ones, and the tick ends with the new ones.
- **A select holds what its player controls.** A select of a dead unit, an enemy's unit and two of its player's own keeps its own two, in increasing stable id; a select past one payload continues in the next input.
- **A predicting client commands what the server does.** A client's select and order predict the server's start of the order, and a rollback keeps the units it commands.
- **The client moves a hundred units.** In the client, the player moves a hundred units of a base start, and the log shows no dropped order.
