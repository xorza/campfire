# Campfire — QUIC transport

The server and the client link over QUIC alone, through `quic`, an IO layer on `quinn-proto` under Lightyear's `Link`, in a crate of its own that `net` uses. QUIC alone, not WebTransport: WebTransport is HTTP/3 over QUIC, and its one gain is that a browser reaches it, which Campfire dropped ([Code](../../AGENTS.md#code)). The facts behind each decision are in [the research](../research/quic.md).

## Decisions

### The stack

- **D1. QUIC on `quinn-proto`, in its own crate.** `quinn-proto` is QUIC with no IO, the core of `quinn`, over `rustls` and `ring`, with RFC 9221's datagrams and TLS's exporter. Not `quinn`, whose API needs an async runtime; not `noq`, whose multipath and NAT traversal no slice needs yet; not `quiche`, a C library with no exporter; not `s2n-quic` or `neqo`, with their own IO or NSS; not Lightyear's UDP, with no encryption or congestion control, nor its netcode, whose tokens need a second protocol. `campfire-quic` depends of Campfire's crates on `common`, `store` and `log` alone, so it holds no game type, and `net` keeps what is Campfire's: the server's key and the meaning of a close.
- **D2. The socket is `quinn-udp`'s.** It reads and writes in batches, turns on ECN, and gives each datagram's destination, so a server bound to `0.0.0.0` replies from the address the client reached; it keeps its OS files behind one API ([Platform](02-engine-core.md#platform)). The server binds before its app runs, so a port in use ends the start with an error naming the address. A client binds port 0 of its server's address family.
- **D3. A thread for each endpoint, and the frame does no IO.** The thread waits through `polling` for the socket, the earliest deadline, or a wake, a byte the app sends from one loopback datagram socket to another that the poller watches, as the self-pipe trick does: `polling`'s own `notify` allocates on each call on kqueue, as on macOS; it reads one batch with no lock, takes the mutex it shares with the app for that batch, and writes after it lets go. So acknowledgments and keep-alives go on through a stalled frame, and a frame waits at most one batch for the mutex. The frame moves datagrams between the connections and Lightyear's links, in `BufferToLink` and `LinkSystems::Send`, and wakes the thread once. A link that unlinks empties its two queues: what they hold is its connection's, and Lightyear, which reads them only while the link is linked, would give it to the next connection, as a pong of a ping that connection never sent. The queues between the two are `quinn-proto`'s own, bounded; no channel and no runtime. As `quinn-proto` takes each datagram by value, the thread copies each read into a ring of four arenas of 256 KiB, and a datagram is a view of its arena; the ring reuses an arena once each of its datagrams dropped, a frame after its read, so a read allocates only when the frames fall behind or a message slice Lightyear keeps holds an arena. An endpoint's drop joins its thread. A thread whose socket fails ends each connection, and the next frame ends each link with `LinkEnd::SocketFailed`, as only the thread drives the connections' timeouts; a thread that panics passes its panic on at the next frame.
- **D4. Datagrams, not streams.** One Lightyear packet is one DATAGRAM frame: Lightyear keeps reliability, order and fragments, QUIC keeps encryption, congestion control and the path MTU. The transport parameters let the peer open no stream, as the IO would read none. A full send queue drops its oldest datagram, as the newest state matters most.
- **D5. A link's minimum MTU is QUIC's datagram.** `LINK_MIN_MTU` is `1200 − (1 + 8 + 4 + 16) − 9 = 1,162`: QUIC's minimum path, a short header with ids of 8 bytes, a packet number of at most 4, an AEAD tag, and the DATAGRAM frame's type and length. Every link takes it from its spawn, in-process ones too, as Lightyear fixes a link's fragment size when its transport is added, and both ends must agree. The current MTU follows the connection's `max_size`. A connection whose datagrams cannot carry `LINK_MIN_MTU` on the minimum path is closed: only a peer with longer ids or a smaller `max_datagram_frame_size` makes it so.

### The server's key

- **D6. A raw key, derived from the server's key.** The server presents an Ed25519 key with no certificate ([RFC 7250](https://www.rfc-editor.org/rfc/rfc7250)), as no client reads a certificate's names or dates. Its seed is HKDF-SHA256 of the server's own key, label `campfire/tls/v1`: one secret file, so the pin cannot be lost while the identity stays, and no expiry. The listing names it as `TlsKey`; the client's verifier takes that key alone, and refuses any other with TLS's `access_denied`.
- **D7. TLS 1.3, ALPN `campfire`, no client key, no resumption.** A player proves its key by the connect answer, not by TLS. No session ticket, so every handshake presents the key and the verifier checks it, and no early data.

### Connections

- **D8. Retry, tokens, migration, and resets after a restart.** The server answers each new address with a stateless Retry ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000) §8.1), so a spoofed address costs no state. Each connection gives its client two `NEW_TOKEN` tokens (§8.1.3), bound to its IP, which let its next connection from that IP within two minutes, a session's default restore window, skip the Retry's round trip; the server keeps each used token's nonce until it expires, so a token works once. A token outlives no server, as its key is new at each start. 0-RTT would gain no round trip: the connect answer signs the TLS exporter, which only the completed handshake gives (D11). Keep-alive 1 s, idle timeout 5 s. A client whose NAT moves it keeps its link. The stateless reset key is HKDF of the server's key, label `campfire/quic-reset/v1`, so a server started again resets its old connections at their next packet (§10.3), and clients rejoin at once.
- **D9. The endpoint owns the connections; a link's entity is its peer.** The endpoint holds its connections in a table by handle. A server takes connections from its `LinkStart` to its `Unlink`, and spawns a link's entity only once a handshake completes, whole, its `RemoteId` the entity itself: an address is no peer, as QUIC holds two connections from one address and moves one to another, and Lightyear's patched raw server keeps that id. A link entity holds its endpoint weakly; its removal, by any path, closes its connection.
- **D10. A link's end is a type.** A link holds `LinkEnd` from its unlink to its next link: how the IO lost it, or `Closed` with the code its own end closed it with. `CloseLink` closes with an `AppCode`, which the peer reads back; codes below 16 are `quic`'s, `net`'s `CloseCode` names the rest, and `LinkLost` logs a `LinkLossCause`. So a peer that ends a link ends the other at once, and says why; an app's exit closes every connection with `STOPPED`. A close that a peer sends before its handshake is confirmed goes in the handshake's packets, which carry no app code: QUIC sends it as `APPLICATION_ERROR` with no reason (RFC 9000 §10.2.3), and the link ends `ClosedInHandshake`.

- **D13. Limits for each address, from the session's seats.** No address of honest players needs more live connections than the session has seats, its slots and its most spectators, which the server gives its endpoint as its `AddressLimit`, with its grace period, as its bound socket starts to serve; an IPv4 address, one mapped into IPv6 among them, or an IPv6 /64, which one host often holds whole, holds at most that many connections not closed. Its new handshakes come from a bucket of the same size, each handshake back after its share of the grace period, as the generic cell rate algorithm keeps a token bucket in one number, the time it is full again, counted exactly in nanoseconds times the seats; so a household whose link dropped rejoins at once. A connection past either is refused, `CONNECTION_REFUSED`, before its handshake, after its Retry, so the refusal costs no signature; a refused connection takes nothing of its bucket. A loopback address holds no limit: its peer runs on the server's own host, which can starve the server by other means, and a LAN check plays every client there. A carrier's NAT that puts more players behind one address than a session has seats meets the limit, which is the one cost; a connection whose peer vanished counts until its idle timeout closes it, 5 s.

- **D14. A flood of handshakes is bounded, measured, and met by a puzzle only when needed.** A handshake runs on the endpoint's thread under the mutex the frame takes (D3), so a flood of them from many real addresses, which the Retry and D13's limits let through, would hold the frame for its batch; a pass takes at most so many new connections, a count a bench of the flood sets, and the rest wait for the next pass. A puzzle comes only once that bench shows a flood within an attacker's reach starves the server, and then as IKEv2's and Tor's are: dormant at effort 0, raised by a control loop under load, before the handshake it spares, the requests served by the effort each proved and none banned for an answer it never sent, memory-hard so a GPU gains little ([research](../research/quic.md#client-puzzles)). No puzzle stops a flood of bandwidth, which the network before the server stops.

### Reachability

- **D12. A server maps its own port.** A server behind a home router asks the router to forward its port, on a thread of its own, `PortMap`, which the server starts once its socket is bound and which holds no lock the frame takes. In turn, each with its own short tries, so the first that answers wins within seconds: PCP's `MAP` to the default gateway, which `netdev` names; NAT-PMP when the gateway answers PCP with version 0; UPnP-IGD through `igd-next`'s blocking API, the router found by its answer to an SSDP search or by its `NOTIFY` announcement, whichever comes first: a host firewall that tracks connections drops an answer a router sends from a port other than 1900, as TP-Link's ER605 does, and lets the multicast announcement in. A router found by its announcement is built from the description and the service schema at its location, as `igd-next` builds one only from a search, on a socket that shares port 1900 with the host's other listeners, `store`'s `SharedPort` ([Platform](02-engine-core.md#platform)): an announcement is a router's only when it says the gateway or its WAN connection is alive at a location of its sender's own address, as `igd-next` trusts a search's answer; its description and service schema are read over HTTP, no redirect followed, each within 1 MiB and an XML nesting of 64, as `igd-next` bounds its own, every URL of them at the router's address. The thread waits for its next turn and for announcements at once, and an announcement of a router at an address not heard before, while no router maps the port, starts a turn at once, so a host that varies its location starts one turn at most; a turn whose search finds no router maps through the last router heard. Each asks for the socket's own port outside, for 7,200 s, and renews at 1/2 to 5/8 of what it granted, as RFC 6887 §11.2.1 has it; a UPnP router that takes only a lease that never ends gets one. A map that fails is tried again in 30 minutes, or, after a PCP refusal, once the refusal's lifetime ends, as RFC 6887 §7.2 has a client expect the same answer until then, and at most the 7,200 s it asks for, as a router's refusal may last for years; a server started again meets one for the mapping its last run left under that run's nonce, which forwards to the same port meanwhile. A renewal that fails starts the turn again. The server logs the external address and port the router gave, the address a player outside joins at; when the router's own address is private, of RFC 1918 or carrier-grade NAT's 100.64.0.0/10, another NAT stands before it, and the server warns that a player outside joins only if that NAT forwards the port, but keeps the mapping, as a modem that forwards to the router makes it reachable. Its drop wakes the thread, which deletes the mapping, and joins it: a lifetime of 0 to PCP or NAT-PMP, one try of at most a second; a removal to UPnP, one request, which `igd-next` bounds at 10 s and no caller can shorten. A drop during a turn stops it before its next request, and waits for the request under way: at most 3.75 s of a PCP or NAT-PMP request's tries, a UPnP search of 3 s, or a UPnP request, which `igd-next` bounds at 10 s. Each grant is held as the router makes it, before its address outside is read, so the drop deletes it whether that read came or not. A host forwards the port by hand where no router answers, and `--no-port-map` keeps a server from asking. IPv4 alone: a host on IPv6 needs no translation, and its firewall's pinhole stays the host's; so a server bound to loopback, or to IPv6, which takes IPv4 only where its OS makes the socket dual-stack, maps nothing. `quic` holds the PCP and NAT-PMP messages, and `netdev` and `igd-next` keep each OS behind one API.

### The connect answer

- **D11. The answer binds to the TLS session.** Both ends read RFC 9266's `tls-exporter` binding ([RFC 9266](https://www.rfc-editor.org/rfc/rfc9266)), which the link holds as `LinkBinding`, and the answer signs `"campfire/connect/v2" ‖ challenge ‖ binding`. A party that holds the server's TLS key and relays an answer holds two sessions, whose bindings differ, so the relay fails. In-process links take one fixed binding; the challenge keeps an answer fresh where there is no TLS.
