# Campfire — QUIC transport

Proposal: the server and the client link over QUIC alone, through an IO layer of `net` on `quinn-proto`, in place of Lightyear's WebTransport. WebTransport is HTTP/3 over QUIC, and its one gain over QUIC alone is that a browser reaches it, which Campfire dropped ([Code](../../AGENTS.md#code)). What it costs, from [the research](../research/quic.md):

| Today | What it does |
| --- | --- |
| A tokio runtime for each app that adds the plugin, one worker for each core, leaked | The server's network threads compete with Bevy's task pools; a process adds the plugin once, and the harness and the local server assert that they add none ([Networking](02-engine-core.md#networking)) |
| Two unbounded channels for each packet, to and from a tokio task | A new `Bytes` and a wakeup on another thread for each packet; when congestion control holds packets back, the queue and the delay grow with no bound |
| Lightyear's link packs packets of up to 1,200 bytes; the largest datagram QUIC carries on its minimum path is 1,161 | A larger packet is dropped with a debug log until path MTU discovery raises the MTU, and always on a path that stays near QUIC's minimum, as a tunnel's; a reliable message in it is sent again at the same size |
| An HTTP/3 `CONNECT` after the QUIC handshake | One more round trip at each connect |
| The connect answer binds to the certificate's hash | A party that holds the server's TLS key can relay a player's answer to the real server and take the player's seat ([Connection](05-protocol-spec.md#connection), step 3) |
| A self-signed certificate of 14 days, made again at a start that restores no session | The renewal and the expiry in the `tls` file exist for a browser's rule ([Sessions](10-sessions.md#decisions), Start) |
| `LinkLost` holds the transport's text | The LAN check's impostor must fail, but no code can tell why it failed |

## Decisions

### The stack

- **D1. QUIC alone, on `quinn-proto`.** `quinn-proto` is QUIC with no IO: state machines that take datagrams and the time, and give datagrams and the next deadline. It is the core of `quinn`, the most used QUIC in Rust, over `rustls` and `ring`, which the build holds already; it carries RFC 9221's datagrams and gives TLS's exporter. Not `quinn`, whose API needs an async runtime, where D3 needs one thread; not `noq`, a younger fork of `quinn` whose multipath and NAT traversal no slice needs yet (What waits); not `quiche`, a C library to build, with no exporter in its API; not `s2n-quic` or `neqo`, which bring their own async IO or NSS. Not Lightyear's UDP, which has no encryption, no handshake and no congestion control; not Lightyear's netcode on it, whose connect tokens need an issuer that knows the server's key, a second protocol.
- **D2. The socket is `quinn-udp`'s.** One non-blocking `std::net::UdpSocket` for each endpoint, which its thread (D3) reads and writes in batches through `quinn-udp`. It turns on ECN, which lets congestion control slow down before a loss, and gives each datagram's destination address, so a server bound to `0.0.0.0`, as design 10's unit is, replies from the address the client reached; GSO and GRO where Linux has them. It keeps its OS files behind one API, as std does, so Campfire names no OS ([Platform](02-engine-core.md#platform)). The server binds its socket before its app runs, so a port in use ends the start with an error that names the address, not a server that runs with no link. A client binds port 0 of the unspecified address of its server's family, IPv4 or IPv6.
- **D3. A thread of its own drives it, and the frame touches memory alone.** Each endpoint runs on one `std::thread` of its own, with no runtime, which holds the socket and shares the endpoint and its connections with the app behind one mutex: `quinn`'s shape, with a thread in place of its driver task. The thread waits, through `polling`, for the socket to be readable or for the earliest deadline of its connections, or for the app to wake it. It reads one batch of the socket, `quinn-udp`'s, with no lock, then takes the mutex to give each datagram to the endpoint and each event to its connection, serves each due deadline by `handle_timeout`, and writes what the connections have to send; it takes the mutex again for each batch, so it holds the mutex for one batch at most. Acknowledgments, keep-alives and loss recovery so go on while the app's frame stalls: a frame that stops for longer than the idle timeout, as a window held in a move on Windows, a suspended process or a slow server frame, ends no link, as today's tokio threads end none. The frame does no IO. In `PreUpdate`, in Lightyear's `BufferToLink`, it takes the mutex, moves each connection's received datagrams to its link's receive queue, and takes the endpoint's news into the world: the links made, ended and moved to a new address. In `PostUpdate`, in Lightyear's `Send`, it moves each link's send queue to its connection, then wakes the thread by `polling`'s `notify`, which writes them at once: one wakeup for each frame, not one for each packet. The queues between the thread and the frame are the connections' own, which `quinn-proto` bounds: the received datagrams by `datagram_receive_buffer_size`, which drops the oldest when the frame falls behind, and the sent by D4's queue; no channel grows with no bound. A frame waits for the mutex at most as long as the thread takes for one batch. A write that would block drops its datagrams, which QUIC takes as lost. An endpoint's drop stops its thread and joins it, so no thread outlives its app, where today's runtime is leaked.
- **D4. Datagrams, not streams.** One Lightyear packet is one QUIC DATAGRAM frame. Lightyear keeps what it does over any link, its channels' reliability, order and fragments; QUIC keeps encryption, congestion control, pacing and the path MTU. A connection opens no stream, and its transport parameters let the peer open none, so a peer that opens one breaks QUIC's stream limit and ends its connection: `quinn-proto`'s defaults let a peer open 200 streams whose data the IO would never read. When congestion control holds datagrams back, a connection keeps at most `datagram_send_buffer_size` bytes of them, and a new datagram pushes the oldest out: the newest state matters most, and Lightyear sends a lost reliable message again. Memory is bounded; the delay a full queue adds is its size over the connection's sending rate, so the size waits for a measurement (What waits), and until then it is `quinn-proto`'s 1 MiB.
- **D5. The link's MTU is QUIC's datagram.** A link's minimum MTU, which Lightyear's fragments take on both peers when the link is made, is the largest datagram on QUIC's minimum path of 1,200 bytes: `1200 − (1 + 8 + 4 + 16) − 9 = 1,162` bytes, from a short header with the endpoint's connection ids of 8 bytes, a packet number of at most 4 and an AEAD tag of 16, and a DATAGRAM frame's type and largest length. Both ends set the id length, so the number holds on every link of two Campfire ends, and a test checks it against `quinn-proto`'s `max_size` on a connection once its handshake completes, before discovery. Every link of Campfire takes `LINK_MIN_MTU` as its minimum from its spawn, so its two ends derive one fragment size whatever IO links them: the client's entity, whose `Transport` fixes its fragment size as `SimClient::spawn_client` spawns it, before an IO exists, and the in-process links of the harness and the local server. The link's current MTU follows `max_size` each frame, as path MTU discovery raises it and black hole detection lowers it. A connection whose `max_size` falls below `LINK_MIN_MTU`, at its handshake or later, is closed: only a peer that gives connection ids longer than 8 bytes, or a smaller `max_datagram_frame_size`, makes it so.

### The server's key

- **D6. The server presents a raw key.** The server's TLS identity is an Ed25519 key with no certificate ([RFC 7250](https://www.rfc-editor.org/rfc/rfc7250)): a self-signed certificate's names and dates are checked by no one, as the client trusts the key its listing pins. The key's 32-byte seed is derived from the server's own key, the secret of its `key` file, by HKDF-SHA256 ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)) with no salt and the label `campfire/tls/v1`, so the server keeps no `tls` file: the two keys were made once and kept in one directory and one process alike, so a second file adds a format, and a way to lose the pin while the server keeps its identity, and protects nothing. There is no expiry and no renewal: the 14 days were WebTransport's rule for a browser. The listing names the public key, 32 bytes as 64 hex digits, `TlsKey` in `protocol`, in place of the certificate's hash. The client's verifier takes only the pinned key, and refuses any other with `rustls`'s `ApplicationVerificationFailure`, which TLS sends as the `access_denied` alert. The TLS key changes only with the server's key, so a restored session's clients keep true pins, and a host that wants a new TLS key makes a new server identity.
- **D7. TLS 1.3, one protocol name, no client key, no resumption.** QUIC runs only TLS 1.3; the ALPN is `campfire`, which RFC 9001 requires, and the engine release stays the offer's check. The client presents no key to TLS: a player proves its main key by the connect answer, as before. The name a client sends is fixed, and its verifier does not read it. The server sends no session ticket and the client keeps none, so every handshake presents the server's key and the client's verifier checks it: a resumed handshake presents none, and the pin of a client that resumes is checked by no one at that connect. No ticket means no early data (What waits).

### Connections

- **D8. Each new address proves itself, a link outlives a new port, and a restart resets.** The server answers each first packet from an address that has not proved itself with QUIC's stateless Retry ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000) §8.1), so a spoofed address costs it no state, as design 05's step 5 asks: one round trip at connect, as WebTransport's `CONNECT` costs today. The server sends no `NEW_TOKEN`, so every connection, a reconnect too, takes the Retry. Keep-alive is 1 s and the idle timeout 5 s, as today ([Sessions](10-sessions.md#decisions), Clients). A client whose NAT gives it a new port keeps its link, as QUIC migrates the connection, and its `PeerAddr` follows. The endpoint's stateless reset key is derived from the server's key as D6 derives the TLS key, with the label `campfire/quic-reset/v1`, as RFC 9000 §10.3 has an endpoint do that resets connections after it lost them: a server started again on its data directory answers each old connection's next packet with a reset, and its clients rejoin at once, not after the idle timeout.
- **D9. The endpoint owns the connections, and a link's entity is its peer.** The endpoint, on the server's entity or the client's, holds a table of its connections by `quinn-proto`'s handle, so each event reaches its connection with no search; its thread holds the socket (D3). A server spawns a link's entity only once its connection's handshake completes, with all it needs in one spawn: `LinkOf`, a `Link` of `LINK_MIN_MTU`, `PeerAddr`, the connection's handle, `ChannelBinding` (D11) and its `RemoteId`; a handshake that fails leaves no entity. The removal of a link's entity closes its connection, whatever removes it: an `Unlink`, the server's end, which despawns every `LinkOf` in the same flush, or a despawn; the endpoint keeps the closed connection until it drains, and its thread answers the peer's packets until then. A peer's id is its link's entity, `PeerId::Entity`, not its address: QUIC holds two connections from one address, as when a client connects again from its socket while the server still holds its old connection, and an address changes as a connection migrates, while Lightyear's peer map and replicon's `NetworkId` take one link for each id, and `PeerId::Raw` folds an IPv6 address. Lightyear's raw server keeps the `RemoteId` the IO gives, as its raw client does: a change to the patched Lightyear.
- **D10. A link's end is a type.** The IO puts `LinkEnd` on a link's entity before it unlinks it: `TimedOut`, `ClosedByPeer` with the peer's `CloseCode`, `WrongServerKey`, `Refused`, `Reset` and `Transport` with QUIC's error code, from the connection's error and the alert of D6. The end that closes a link says why, by `net`'s `CloseLink { entity, code }`, which the IO takes and passes on to Lightyear's `Unlink`: a `CloseCode`, `Left`, `Superseded`, `InputRefused`, `ChainRewritten` or `Stopped`, which QUIC carries as the application's error code, and a code the peer does not know reads as `Transport`. Each place that unlinks with text today names its code. `LinkLost` becomes an enum of its causes: the IO's `LinkEnd`, and the client's own, `ChainRewritten`, `Superseded` and the end of its retries; the LAN check's impostor must end by `WrongServerKey`. Lightyear's `UnlinkReason`, which holds text, stays Lightyear's own for its logs. A closed connection reaches the peer, which ends at once, not 5 s later. An app's exit closes each connection with `Stopped`, and the endpoint's drop waits until its thread wrote the closes, not until they drain, then joins it.

### The connect answer

- **D11. The answer binds to the TLS session.** Each end reads, once the connection's handshake completes, the `tls-exporter` channel binding of [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266): 32 bytes of TLS's exporter, label `EXPORTER-Channel-Binding`, empty context, which the IO puts on the link's entity as `ChannelBinding`, in the server's spawn of the link and on the client's entity as it links, so no connected link lacks one. The answer is a signature over `"campfire/connect/v2" ‖ challenge ‖ binding`, and the server checks it with its own link's binding. A party that holds the server's TLS key and stands between a client and the server holds two TLS sessions, whose bindings differ, so an answer it relays fails; with the certificate's hash, it passes. An in-process link has no TLS: the harness and the local server put one fixed binding on both its ends, as they share one certificate hash today. The challenge stays: it keeps an answer fresh on a link with no TLS.

## What changes elsewhere

- **Design 02.** `net`'s row and the Networking paragraph: QUIC through `net`'s IO, one thread for each endpoint, with no plugin rule and no runtime; the LAN check's row and its impostor; the libraries table gains `quinn-proto`, `quinn-udp`, `rustls` and `polling`; Secret files: the server's TLS identity leaves the list; Outside the gateway: the cached TLS identity goes.
- **Design 05.** The Connection's steps 1, 2, 3 and 5, and the listing's TLS key in place of the certificate's hash.
- **Design 10.** Start: the server keeps no `tls` file, and its TLS key follows its key; Clients: the keep-alive and the idle timeout are `net`'s, and a server started again resets its old connections.
- **Lightyear.** The patched fork's raw server keeps a `RemoteId` its link holds (D9).
- **The build.** `wtransport`, `aeronet_webtransport`, `quinn`, `rcgen` and tokio leave it; Lightyear's `webtransport` feature goes. `rustls` comes in with no default features, with `ring` and `std`, and `quinn-proto` with `rustls-ring` alone: `rustls`'s defaults bring `aws-lc-rs` and TLS 1.2, and `quinn-proto`'s `bloom` brings the `NEW_TOKEN` that D8 sends none of.

## What waits

- **Limits for each address.** Design 05's limits on connections and packets for each address: players behind one NAT share an address, so a count of connections from one address refuses them; a limit is set against a measured flood.
- **NAT traversal.** A home host forwards a port or uses UPnP, as design 05's step 4 says; `noq`'s NAT traversal and multipath are its options.
- **The IO's cost.** A bench case of the frame's two systems and of the thread's batch, the frame's waits for the mutex, and what `quinn-proto` allocates for each packet, measured in an optimization session.
- **The send queue's size.** `datagram_send_buffer_size`, set from a measurement of the delay a full queue adds on a slow link (D4). Lightyear sends a reliable message again after 1.5 round trips, and does not know that its last copy still waits in the queue, so a queue longer than that holds copies.
- **0-RTT.** A reconnect that sends data in its first flight risks a replay of it, and needs the session tickets D7 sends none of; a reconnect takes one round trip and the Retry's.
