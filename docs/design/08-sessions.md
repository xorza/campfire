# Campfire — Sessions

How a session outlives its server process, its players' links and its players.

## Decisions

- **A private journal makes the log durable.** The server appends each record to a journal of framed, checksummed records and syncs it on a background thread, as SQLite's WAL and LevelDB's log do; a restart reads it to its last whole record. The published log is written at the end from the journal's whole frames, so it keeps one canonical file and no torn record reaches a verifier.
- **The journal belongs to the server's session.** The journal, its frames not yet written and the durable heads of each player slot's chain are one value only a server's session holds, which the session gives each call of its log that takes a record, so a verifier's session holds none and its log keeps no state of a server. Refused: the journal inside the log, which made every verifier's log carry a journal to skip.
- **A record is encoded once.** The log encodes each record once into its own buffer, which its file's count measures, a server input's signature covers with the place before it, and the journal copies into a frame; the journal hands the sink a server frame's records in one append, so its writer wakes once a frame, not once a record. Refused: one encode for the file's count, one for the signature's message and one for the journal, and a wake for each record.
- **The replay is a cursor the session owns.** A replay's state, the next tick it seals and a schedule of its own that the log's entries drive again, is a value beside the log in the session, which the tick pulls each tick's inputs through and which goes once the replay reaches the log's next tick, so a verification, a restore or a load runs on live in the same session, the log at its end throughout. Refused: a cursor that borrows the log, which no Bevy resource can hold beside the log it borrows; and the log rewound in place, which made it both a record and a cursor whose readers had to know which.
- **The live log is its latest checkpoint's state and the entries since.** As Raft keeps a snapshot and the tail of its log, a server's log forgets, as each checkpoint's record comes, what it took before that checkpoint's boundary, which its journal holds: the entries, the ticks' ends, and the inputs but those still to apply; its player slots' control, its schedule, its delegations, its player slot changes, few in a session, and its segments stay. A log with no journal, a verifier's, keeps every entry, as nothing else holds them. Refused: every entry of the session in a server's memory, which grows with the session.
- **What reads the past reads the carry.** A load goes back to a save from that checkpoint's carry and the log's own counts at its boundary, not from the log's own past decoded again, so no decode trusts a signature it does not check. Refused: the journal read again at a load, a file read on the tick's thread; and a decode of the log's past that trusts its signatures, a mode its other calls must know.
- **A log takes a carry only once checked.** A carry is a `CheckedCarry`, made only by its check of every count against the boundary's ticks and the session's input rules, its chains against their player slots and stamps, its main keys against each other and its inputs against their player slots, ticks, order and lengths, as the live log checks a packet; the log's own carry at a load passes the same check. Refused: a check of the player slot count and the inputs' player slots alone, after which a signed carry of a chain at `u64::MAX` inputs panicked the verifier.
- **A published log is written from the journal.** At the session's end a reader streams the journal's frames once to count what the file's counts need, the segments, the ticks of each and the entries of each tick, each load's cut applied, then once more to copy each record the file keeps, so the memory it takes is a frame's and the counts', not the session's. Refused: a log rebuilt whole from the journal and encoded, which holds the session in memory once more; and the file written from the live log, which then must hold the whole session.
- **A checkpoint copies only what changed.** At a boundary the main thread encodes the changes since the last checkpoint into a delta, and a background thread applies it to its own copy, then encodes, hashes and writes the snapshot, so no tick waits for a world's snapshot.
- **Every state write marks its component changed.** The copy trusts Bevy's change ticks, so no state type may change while its change tick stays, and no state type holds interior mutability; a test compares the copy with a full snapshot every tick.
- **Bots are server player slots.** The host gives each player slot as a player, a bot or open; the server makes a bot's inputs and signs them, and a mode's bot or an order script drives it (A mode names its bots).
- **The mode decides who may take a player slot.** Its `[players]` gives late joins, bot takeovers and what a leaver's player slot becomes; the host gives the grace period and the restore window.
- **The host picks, and the terms record the pick.** The terms hold the place of each option's picked value, the mode's options by name ([Keys](05-protocol-spec.md#keys)), as Zero Hour's options string carries its starting cash, `SC=`, to every player and into its replay's header, and OpenRA's lobby settings hold each option; a place, not the value, as the mode's fingerprint fixes the values, and the rules refuse another count or a place past an option's values, as they refuse a visibility the mode does not admit.
- **The terms hold each player slot's picks.** The session terms hold the place of each player slot's pick of each choice, an unpicked player slot's as none, as Zero Hour's start string holds each slot's `PlayerTemplate` beside its options, OpenRA's lobby `Session` each client's `Faction` and Spring's start script each team's `Side`; the host gives them on its command line, a client that hosts its own server its own and its bots', and the build fills the choices before `on_match_start`. Refused: a lobby that holds the match until each player slot joins with its picks, which redesigns the session's start; a pick at the first tick, a pick phase the original does not have.
- **A pick is given by its value.** The server's and the local client's `--option <name>=<value>` names one of the option's values, an option not named its default; a name the mode lacks, a value its option lacks, or picks a waiting session does not hold are refused before a session opens, as another map is.
- **A restore keeps its visibility.** A host's `--visibility` or `--spectators` that do not give the waiting session's visibility are refused before it restores, as other picks and another map are; nothing asked restores it as it was. Refused: the session's own kept with no word, which hid what the host asked.
- **Pause and game speed on the local server only;** neither enters the log.
- **A burst after a stall runs 9 ticks at most.** One server frame runs at most 9 ticks, 300 ms at 30 ticks a second, the rest of its time dropped and logged, so a frame costs at most 9 ticks' work, as fixed-timestep loops do (Fiedler's *Fix Your Timestep*). Refused: no bound, under which each long frame makes the next longer.
- **A key has one owner.** A key goes from its file into its signer, which is not `Clone`, is shared by `Arc` and erases the key as it drops; a secret is not `Copy`, is zeroed as it drops and compares in constant time, as `secp256k1`'s `SecretKey` does. Refused: keys and seeds as `Copy` values, whose copies no one can find to erase.
- **Keys are plain key files.** A secret key is an `nsec` in a file only its owner may open; a file others may open is refused on every OS, as OpenSSH refuses a key with loose permissions. Encryption by NIP-49 comes with `identity`.
- **A journal that fails ends the server.** A failed write or sync is never retried: Linux may drop the pages a failed fsync held, so a retry can succeed over lost data, as PostgreSQL's fsyncgate showed. The host's supervisor starts the server again, and the start restores the session; the server never restarts itself.
- **A disk that stops is a journal that fails.** A write and its sync that run past two minutes, as long as Linux's hung task detector waits, or records that pile up past a bound while the disk falls behind, fail the journal as a failed sync does; a writer that waits on the disk forever, as PostgreSQL's does, keeps receipts back and memory growing with no report.
- **The newest login wins.** A join of a main key whose player slot has a live link ends the old link and places the new one, as game servers do, so a player who comes back is never locked out by a link the server has not yet seen fail.
- **A player slot's link has one record.** The server's `PlayerSlotLinks` holds each player slot's link, so of two logins of one main key in one frame, the later in the door's order dismisses the earlier, and a link's `PlayerLink` keeps only the player slot and team its inputs read. Refused: a Bevy relationship from the player slot's entity to its link, as the door's commands apply after the frame's joins, and a second join would read the old link unless the door kept a third record or placed through the world at once (2026-10-17).

## Player slots and controllers

- **The log knows each player slot's controller,** from its own records, with no package, so a verifier checks every packet against its player slot's player.
- **A player slot's units stay its own whatever controls it,** so the mode's rules see one player.
- **A mode names its bots.** A mode's data lists its bots, each a script and its params, and a host gives a player slot one of them by its name: `--server-bot <player_slot>=<bot>`; a player slot of exact inputs at ticks takes an order script by `--server-orders <player_slot>=<file>`. Refused: a bot by its file's path, which a host must find in a package; one flag for both, whose value a parser must guess.
- **A bot's names resolve in the load's books.** The server resolves each bot's script before any session opens, in the books the mode's load built and keeps, at its fastest rate, as a book's rate changes its times and never its names; a script that names what the mode lacks fails the server's start. Refused: books built again for the names, which repeats the load's work; the match's books, which exist only once a session picks its rate, so a bad name would show at a match's start.

## Crash restore

- **A journal is cut at its first bad frame.** A restore keeps the frames before the first torn or corrupt one, cuts the file there and logs what it dropped, as RocksDB's default `kPointInTimeRecovery`; refused: refusing the whole journal, which loses the session to one bad byte, and skipping bad frames, which replays a log with a hole in it.
- **The terms are the journal's.** The private record holds the seed chain alone, and the journal's signed header is the one record of the terms; a restore refuses a seed chain the terms do not commit to, and a journal of another session than its directory's. Refused: the terms in both files, which a restore read from one and ran from the other.
- **A restore window from the journal's last write.** A server back within it replays the session from its latest checkpoint; one back after it aborts the session and publishes its log.
- **A stop is an exit, not a crash.** The first stop signal ends the frame, closes each link with `STOPPED` and deletes the port mapping; the session stays in its journal and restores on the next start.
- **Clients back with full jitter.** A client whose link fails tries again after waits that double to 8 s, each drawn at random below its bound, as AWS's full jitter, so clients that lost one server do not all return in one instant.

## Reconnect and late join

- **A returning client resumes its chain.** A client that holds its chain's history cuts it back to the head the log holds; one with no history takes the server's head, as the signatures already logged cover every earlier input.
- **A grace period before a leave.** A player whose link fails keeps the player slot for the host's grace period, measured by the server's monotonic clock.

## Receipts

- **A receipt names only what a crash cannot lose.** Only inputs whose journal records are synced count. It promises that they survive a crash, not a disk that corrupts them: a restore that cuts at a bad frame drops every input after it, receipted or not.

## Checkpoints

- **Restore equivalence.** A match restored from a checkpoint plays the same ticks to the same hashes as the match that made it; every gap a test finds is closed as state, or as derived data rebuilt after a restore.
- **A checkpoint never waits for the last.** The log keeps the checkpoints begun in the order they began, and their records come in that order, so a checkpoint due while the last one's snapshot still syncs begins at once. Refused: one checkpoint begun at a time, which made the tick at the boundary wait on the last snapshot's fsync.
- **A log file may start at a checkpoint.** A verifier checks its base against the segment's signed checkpoint record before it replays, as Ethereum's checkpoint sync starts from a signed state. Refused: a server's journal for verifiers, whose state a verifier must not trust.

## Saves and loads

- **A load keeps its random outcomes.** A load cuts the log back to the save, whose segment keeps its number and seed, so the published log's segments stay consecutive and a load meets the same random outcomes for the same inputs, as XCOM's saves do.
- **A load goes back in place.** A local server's load keeps its session, its live log and every link: it despawns the match's entities, clears each module's derived state as its declarations say, each cache by a `clear` the `Cache` trait holds with no default, and restores the save's snapshot into the same world, as OpenRA builds a new `World` over the same `OrderManager`; its clients learn of it by `MatchLoaded`, drop their match and join again over their links. A test holds that a match loaded in place plays as a fresh restore of the same save, tick by tick. Refused: a new server app restored from the journal, which reads the journal again at a load and drops every link (What reads the past reads the carry); a world built anew beside the old, which the network layer's resources would have to move into.
- **Saves run on one release** until converters come with signed releases.

## Links

- **A raw key derived from the server's key.** The server's secret for the stack's UDP is its own signing key, from which the stack derives its raw TLS key and its reset key ([One server secret derives the raw key and the reset key](11-net-stack/udp.md#trust)), so one secret file holds the identity and the pin cannot be lost while the identity stays; a listing's `TlsKey` is that raw key's public half. Refused: a TLS key of its own, a second secret file whose loss changes every pin.
- **A delegation's expiry bounds the connect.** A delegation admits a connect, and a join through a new link, until its `expiration`; a player slot it admitted plays on past that time, and a client that joins again within a minute of it delegates a new session key, which the log takes as a `Renew`. As SSH checks a certificate's `valid before` and SMB a Kerberos ticket when a user authenticates, not at each request ([PROTOCOL.certkeys](https://ftp.riken.jp/NetBSD/NetBSD-release-9/src/crypto/external/bsd/openssh/dist/PROTOCOL.certkeys), [NetApp](https://kb.netapp.com/onprem/ontap/da/NAS/Why_is_Kerberos_authentication_working_when_machine_account_is_deleted)). Refused: a check of each input against the server's clock, which a verifier cannot repeat, as the log holds no time; a link that ends at the time, which drops each player of a long match at once.
- **The answer binds to the TLS session.** The connect answer signs the link's `ChannelBinding`, RFC 9266's `tls-exporter`, so a party that holds the server's TLS key and relays an answer holds two packet sessions, whose bindings differ, and the relay fails. The singleplayer link is sealed as a network link is, so every answer signs a real binding. Refused: a plain singleplayer link with a fixed binding, a stand-in only singleplayer signs.
- **Limits for each address, from the session's player slots.** No address of honest players needs more live links than the session has player slots and spectators, so the stack's admission holds at most that many for an IPv4 address or an IPv6 /64, and as many handshakes, which come back over the grace period.
- **A link's end is a type.** Campfire ends a link with a `CloseCode`, which the stack carries as its `AppCode`, and a client's lost link keeps its cause, so a peer that ends a link ends the other at once and says why, and a client tells a refused key from a lost network. Refused: a close with no reason, which leaves the other end to wait for its timeout.

## Local server

- **Singleplayer is a local server.** A singleplayer client runs the server as a thread, with its player in player slot 0, or as its one spectator when it watches, as Veloren and Minecraft do: one code path for singleplayer, LAN and online play ([Precedents](../research/precedents.md)). Refused: a client inside its server's app, which no mode needs.
- **A local session may hold bots alone.** On the local server, a plan of no player slot opens, its match starts as its watcher joins, so the watcher sees it from its first tick, and it ends as its match ends or its client closes it, as no player is left to leave, as OpenRA's skirmish server starts a game of bots while its host spectates and shuts down as its host leaves ([Test matches](../research/test-matches.md)). The dedicated server still refuses a plan of no player, as OpenRA's dedicated server needs human players unless its host sets `EnableSingleplayer`. Refused: a match that starts as its lobby opens, before the watcher's link joins, which shows a match already under way; a player slot of a player who never plays, held for the watcher, which the log would record as a player and which takes a start a two-player map lacks; a dedicated server's watch, which no test needs yet.
- **A local watcher takes no player slot and sees every unit.** With `--spectate`, the local client holds no player slot, so a server bot may hold player slot 0, and the local server admits its one spectator, who sees every unit through any fog, as a test watches both bases, so the client refuses `--watch` there. Refused: all teams' views, as a Dota 2 spectator picks, which hides what neither team sees; a dedicated server beside the client, where singleplayer is a local server.
- **One in-process link.** A singleplayer client and its local server link through the stack's emulator on the OS clock with a perfect model, the stack's one in-process IO. Refused: an in-process channel beside the emulator, a second IO of the same behaviour.
- **The pace sets the tick rate.** A local match's speed gives its client and its local server the match's rate times the speed through the stack's `SetTickRate`, which `Time<Fixed>`, the timelines and the sync all read, while the sim's own rate stays the session's. Refused: a relative speed of `Time<Virtual>`, which the stack's conversions of time to ticks would not see.
- **The log is the local server's, published at the report's tick.** The client's local server settles its journal and publishes the log so far, its seed revealed, as its session's end publishes it, so the log replays to the report's tick; a load before the log reaches that tick drops the report's log, as the log then reaches it in another history. A remote session's report names its session and its tick, which the server's log holds once the session ends. Refused: a save, which holds the state at the tick but not the history that led to the bug; the client's own copy of the inputs, which lacks the other players' and the bots'.
- **The client opens a report.** `campfire-client report <report>` opens it on a local server of the data directory that holds it, whose key signed its log, as a client pins its server's key: the server replays the log through the report's tick before its first frame, as a restore replays its journal, holds the pace paused there, and runs on to the log's end at the pace, its session a verifier's, which logs and signs nothing, with no player, bot, journal or checkpoint, and its door admitting the one spectator, who watches every unit from the camera the report's rig gives back; a report the spectator takes there holds the whole log, so it replays as the one it opens. Refused: a session that plays on from the report, which needs the seeds of segments the log does not reveal and a log format that starts from another session's snapshot; a replay in the client, whose world the network feeds.
