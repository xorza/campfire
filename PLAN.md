# Plan — next steps

The concrete steps of the current stages of the [roadmap](ROADMAP.md), in order, open items only: remove a step when it is done, and a section when it is empty. Each step ends with the check chain passing for the crates it touches, and a stop for review. A later stage's steps come here when it starts, after its design step ([Workflow](AGENTS.md#workflow)).

## Stage 5: MOBA mechanics

Progression first: points and the `learn` order ([Progression](docs/design/04-capabilities/progression.md#rules)). Perks wait for stage 9. Before it, the client's lead as Lightyear keeps it, and the heal timing the combat design states; after it, the verifier on a 3v3 log.

0. **P0. The client's lead** (net, text only): [Bevy](docs/design/02-engine-core.md#bevy) and the comment in `SimClient::build` state the lead Lightyear 0.30.1 keeps: ahead of the server's present tick by half the round trip, a jitter margin, a sync error margin and one tick, and a full round trip ahead only of the newest server state the client holds.
1. **P1. Heals next in the pass** (combat): the damage pass deals a heal that leech or a hook gives next, as [Damage and heals](docs/design/04-capabilities/combat.md#damage-and-heals) says: `PassQueue` keeps the heals the running pass gives apart from its entries, and the pass deals them, in the order given, once the entry that gave them and its events are done, before the next entry. A heal queued before the pass keeps its sorted place, and the path with no scripts deals leech next too. Tests, on the combat fixtures: a leech heal and a hook heal each land before a damage queued earlier in the pass, so a unit that the old order let die lives; two heals of one entry land in the order given. The goldens that change are blessed, each named in the review.
2. **P2. Rank levels** (actions): a slot kind's `levels` becomes a checked type, and the load refuses a list that is not one level for each rank, a level of 0, a level below the one before, `levels` on a kind with no `ranks`, and `levels` in a mode with no `level` track, each by its own load error. The reference 3v3 gets `levels = [1, 3, 5, 7, 9]` on `basic` and `[6, 11, 16]` on `ultimate`. Tests: each refusal, by a table of mode data.
3. **P3. Points** (progression): a `Points` state component on each unit with the `level` track, 1 as it spawns and one more for each level reached there, so an add of experience that reaches three levels gives three. `ctx.learn` spends none. `unit.points`, `unit.track_level(track)` and `unit.xp(track)` run, and the script API reference follows. `Points` replicates, and the client predicts it. Tests: the points at spawn and after a level-up of one and of several levels, the three script names, and a snapshot that decodes.
4. **P4. The learn order** (orders): `Action::Learn { slot }`, checked in Inputs as [Learning](docs/design/04-capabilities/progression.md#rules) says, a dead unit included, and applied in input order with the tick's other orders, before passives hold, so it stops nothing under way. A scripted runner player can send it. Tests: each refusal (another player's unit, a kind with no ranks, the last rank, no point, a level below the next rank's), a dead unit that learns, a cast ordered after a learn in one tick at the new rank, a walk that goes on, and a passive at its new rank in the same tick.
5. **P5. The scripted 3v3 learns** (runner): the 3v3's scripted players spend their points by the learn order, as the rank levels allow, and the match test checks ranks and points at chosen ticks, among them a learn refused for its level. The hero casts stay for the roadmap's 3v3 abilities item. The 3v3 golden is blessed.
6. **P6. Learning in the client** (client, test lane mode): Ctrl and a cast key sends the learn order for that key's slot, and the HUD shows the unspent points and each slot's rank. The lane mode gets a `level` track and experience for kills, and its heroes learn by points in place of its `ctx.learn`, so a LAN playtest can learn. Tests: the key to the order, and the lane mode's scripted match with a learn; its goldens are blessed.
7. **P7. The verifier on a 3v3 log** (verifier): a test verifies the session log of the scripted 3v3 match, learn orders included, with the package store and the seed checks the lane mode's log has, so the new order replays to the same hash.
