# Plan — next steps

The concrete steps of the current stages of the [roadmap](ROADMAP.md), in order, open items only: remove a step when it is done, and a section when it is empty. Each step ends with the check chain passing for the crates it touches, and a stop for review. A later stage's steps come here when it starts, after its design step ([Workflow](AGENTS.md#workflow)).

## Stage 3: Vertical slice, close

1. **Vertical slice playtest, fourth round**: the same 1v1 on LAN, with routes and collision. Units that block each other and body block are new to the feel; write down whether the match reads and plays well. This closes stage 3, or names what is missing.
2. **Collision bench**: on a quiet machine, run `cargo bench -p campfire-capabilities --features bench --bench collision`: 1000 bodies, crowded into 40 m square and spread over 120 m square, contacts found and parted. Check that it fits the Collide stage's share of a tick at 30 Hz, and record the numbers beside the collision design. A timing probe on a busy machine gave 0.14 to 0.42 ms, against 2.1 to 2.5 ms for a check of every pair.

## Stage 4: Game model

Touches: every capability, the registry, the package loader, the client, the reference packages. Design: [The model](docs/design/04-capabilities/00-overview.md#the-model), the capability docs, [Game package](docs/design/03-game-scripting.md#game-package). Each step rewrites the reference packages to the model as it goes, so the 3v3 match keeps running with the same rules; until its step, the code that differs from the design is the code's to fix.

Each step's shape moves into the design when the step lands. Each step ends with the check chain, both goldens and the structure tests ([Structural rules](docs/design/02-engine-core.md#structural-rules)); a step that changes behaviour names the change.

1. **M1: effect lists in the core** ([Effects](docs/design/04-capabilities/actions.md#effects)). Size M. Changes behaviour only where no rule stood: a list whose acting unit is gone.
   - Today the effect lists live in `abilities`, which builds on `combat`. The damage pass cannot run a list, and a mode without `abilities`, such as an RTS of weapons alone, has no lists.
   - `EffectLists` moves to the core's action pipeline. The core holds each list, its names resolved; each effect applies through the effect type of the capability that owns it, as a script call's effects do ([Structural rules](docs/design/02-engine-core.md#structural-rules), the layer rule): `combat` its damage and heals, `stats` its restores and modifiers, `progression` its experience. A list that names an effect of a capability the mode did not declare fails the load, as a section of one does.
   - One rule for a list whose acting unit is gone, as a cast's projectile whose caster despawned: an effect `to = "source"` does nothing, and each other effect applies from no source, as damage whose source no longer exists has none ([Damage and heals](docs/design/04-capabilities/combat.md#damage-and-heals)). Today nothing states it, and no test covers it.
   - Tests: the reference abilities' tests and both goldens pass unchanged; a cast's projectile whose caster despawns before it hits applies its list's damage with no source and skips its effect to the source; the layer test passes with `combat` below the lists.
2. **M2: a weapon's `on_hit` effects and params** ([Weapons](docs/design/04-capabilities/combat.md#weapons)). Size S. Changes the package API: two fields a weapon refused, it now takes.
   - Today the load refuses an effect list and `[params]` on an attack, and the design marks a weapon's `on_hit` as planned.
   - An attack's damage that reaches a unit above zero life queues its weapon's `on_hit` list in the damage pass: after the damage, before `on_attack_hit`, with the target as the unit reached and the attacker as the acting unit. Shields that absorb all of it do not stop it, as the hook's events run then too. Its damage joins the end of the pass at the attack's depth plus one, as a hook's damage does, so a chain stays bounded; a heal, a restore or a modifier applies at once. An extra attack, `ctx.attack_hit`, queues the list too. League of Legends applies on-hit effects whenever a basic attack lands, and Dota 2 its attack modifiers on `OnAttackLanded`.
   - A weapon takes `[params]`, one value each, as its slot kind has one rank: its list's `{ param }` reads them, and so does a modifier it applies, through `ctx.p`. A weapon takes `on_hit` alone of the lists; `script`, `on_resolve` and `on_end` stay refused.
   - Tests: a melee and a ranged weapon whose `on_hit` applies a slow and deals true damage of `{ base = 10, attack_damage = "0.5" }`, with the exact life and the modifier after one attack, its list's damage at depth 1; a target at zero life, and one whose tags block damage, gets no list; a shield that absorbs the whole attack does not stop the list; `ctx.attack_hit` runs the list; a modifier the weapon applies reads the weapon's param; the load refuses `script` and `on_end` on a weapon.
3. **M3: the `purge` effect** ([Effects](docs/design/04-capabilities/actions.md#effects)). Size S. Changes the package API: an effect the load refused, it now takes.
   - Today the load refuses `purge` as planned.
   - `purge = { tag }` ends each modifier of the unit reached whose grants include the tag, whatever its source, at once, as `ctx.remove` ends one. The tag is one the match declares, which the load checks.
   - Tests: a unit with a stun from two sources and a slow, purged of `stunned`, keeps the slow alone, and its derived tags drop `stunned` in the same tick; the load refuses an undeclared tag.
4. **M4: a delivery's hits and sight** ([Deliveries](docs/design/04-capabilities/actions.md#deliveries)). Size S. Changes the package API: `collide` and `sight_radius` go.
   - Today the load takes `collide` and `sight_radius` as planned fields and ignores them, and refuses a `vision` section on a delivery type. Snow Owl, `collide = false`, finds hits on its way that do nothing, and reveals nothing as it flies.
   - A projectile's `hits` takes `none`: it hits no unit and flies to its end. The load refuses `none` beside `width`, `stop_on_hit`, `once_per_cast` or `homing`, and for an action with an `on_hit` list or hook.
   - A projectile or an area type takes a `vision` section; the delivery spawner gives its unit its `Sight`, so it reveals to its source's group while it lasts.
   - Snow Owl becomes `projectile = { speed = "14", hits = "none" }` with `vision = { sight_range = "4.0" }`. The 3v3 golden does not change if no bot casts it; the step says whether it does.
   - Tests: a projectile with `hits = "none"` crosses an enemy's body and ends at its range, no hit recorded; each refusal of `none`; a projectile with a vision section reveals its cells to its source's group in each tick it flies and none after it ends, and an area's the same while it lasts.
5. **M5: the `launch` effect** ([Effects](docs/design/04-capabilities/actions.md#effects)). Size M. Changes the package API: an effect the load refused, it now takes. Needs M1 and M2.
   - Today the load refuses `launch` as planned.
   - `launch = { area, on_hit, on_end }`: an area type of the action's package lands where the unit reached stands, or the acting unit with `to = "source"`, from the acting unit, with the action's params at its rank. Its nested lists run on the units it reaches and at its end; it runs no hook. The lists stay one flat buffer, a launch holding the ranges of its own lists, so a nested list costs no allocation of its own.
   - The step states when a launched area lands: one launched in Hit by a delivery's list, and one launched in Resolve by a weapon's `on_hit`. It writes that into the design, as an area `ctx.area` queues at the same point.
   - Tests: a weapon whose `on_hit` launches a splash of radius 2 that deals half its attack damage: the target takes the attack and the splash, a unit 1.5 m off takes the splash alone, one 3 m off takes nothing, with exact lives; a nested launch two levels deep runs both lists once; `to = "source"` lands it at the attacker; the load refuses a `launch` of a projectile type, and of a type of another package.
